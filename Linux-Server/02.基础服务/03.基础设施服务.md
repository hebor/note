

# DNS服务

计算机网络通信最终都是靠IP定位主机，但对于人类的记忆习惯而言，相比较IP地址这类数字串，人的记忆对字符更加敏感。DNS域名解析服务，是互联网中为域名和IP地址相互映射的一个分布式数据库，核心作用是将域名映射为IP，避免人为直接记忆IP。

## 一、域名层级结构

```
www.pku.edu.cn.
│   │   │   │ └── 根域（通常省略最后的点）
│   │   │   └──── 顶级域：.cn
│   │   └──────── 二级域：example
│   └──────────── 三级域：pku
└──────────────── 主机名/子域：www
```

一个域名的解析过程是从右到左逐层解析，在日常书写域名的过程中，通常都会省略根域的书写，浏览器会自动隐式添加根域。

- 根域：能够解析所有顶级域的服务器IP
- 顶级域 TLD：能够解析所有二级域的服务器IP
- 二级域：能够解析所有三级域的服务器IP
- 三级域：能够解析所有子域级域的服务器IP
- 权威域名服务器：保存某个域名的真正解析记录，是最终答案的来源
- 递归解析器：查询起点，替你"跑腿"。由运营商或公共DNS提供，如`8.8.8.8`（Google）、`1.1.1.1`（Cloudflare）

现在比较常见的域名，一般都是用的主机名+二级域，例如`www.example.com`。

> **FQDN**
>
> FQDN（Full Qualified Domain Name）完全合格主机名，是指**从主机名一直写到根域、能唯一确定互联网上某台主机的完整域名**，FQDN是域名的一种最完整写法。
>
> 在日常工作过程中，我们会更加口语化的称呼“域名”，但实际上指的是FQDN。在概念上，域、域名、FQDN三者是包含与被包含的关系：
>
> | 概念              | 含义                                 | 示例                                     |
> | ----------------- | ------------------------------------ | ---------------------------------------- |
> | 域（Domain）      | 域名空间中的任意一层或一段           | `.com`、`example.com`、`www.example.com` |
> | 域名(Domain Name) | 标识一个域的名字，可以是部分层级     | `example.com`、`www.example.com`         |
> | FQDN              | 从主机名到根域完整写全、无歧义的域名 | `www.example.com`                        |

## 二、DNS查询方式

DNS的查询方式一共有三种，三者在一次典型的未命中缓存的解析里会**串联使用**，而不是三选一。

- 非递归查询：**任意来源** 向 **权威域名服务器或递归解析器** 发起的解析请求，被请求方只用本地数据能够直接解析IP
- 递归查询：**客户端** 向 **递归解析器** 发起的解析请求，必须由递归解析器返回最终的解析IP
- 迭代查询：**递归解析器** 向 **根/TLD/权威** 发起的解析请求，从根域开始层层向下、逐层解析，知道拿到最终IP

客户端操作系统在配置IP信息时，可以选择配置DNS服务器IP，配置的这个DNS的IP就是“递归解析器”，客户端的域名解析都会交给这个”递归解析器“。

## 三、完整的解析流程

以访问`www.example.com`为例：

1. **发起域名解析请求**：浏览器访问该域名
2. **本地缓存检查**：浏览器、操作系统先查自己的缓存，命中就直接用
3. **请求递归解析器**：本地没有缓存时，把请求交给递归解析器
4. **请求根服务器**：得到 `.com` 顶级域服务器地址
5. **请求TLD服务器**：得到 example.com 的权威服务器地址
6. **请求权威服务器**：拿到最终 IP（如 `93.184.216.34`）
7. **返回并缓存**：递归解析器按TTL缓存结果并返回给客户端

> **正向解析&反向解析**
>
> DNS解析有2种方式：正向解析、反向解析。上述解析流程指的是正向解析，即“根据注册的域名查询对应的IP”，反向解析则指的是“根据IP查询对应的注册域名”。
>
> 正向解析和反向解析两者完全独立，包括服务配置、解析记录等信息都是完全独立的。一个很容易误解的点：反向解析不是“正向的反查”，正向解析由域名所有者配置、方向解析由IP段的归属方（ISP、云厂商）授权和配置，域名所有者无权修改反向解析，所以会出现“正向能解析、反向无PTR记录”的场景。

## 四、BIND

在CentOS下DNS的主程序包名称是bind，其服务名称和配置文件名称是named，bind-chroot是出于系统安全性考量的可选安装包，直接使用BIND服务或通过bind-chroot启动dns服务两者可以实现相同的功能，但配置上仍存在细微差异。bind配置文件分2部分，主配置文件/etc/named.conf 和 地址库文件/var/named/（也叫区域数据库文件），配置BIND服务过程中除了配置文件严格的语法格式，还需要注意文件所属用户和组

- bind：DNS主程序包
- bind-chroot：DNS安全包，改变默认DNS根目录，将DNS运行在监牢模式

### 4.1 部署

```bash
# 1.安装软件包
yum install -y bind bind-chroot

# 2.修改主配置文件
cp -p /etc/named.conf{,.bak}
vim /etc/named.conf
options {
        directory       "/var/named";
};

zone "example.com" IN {
        type master;
        file "example.com.zone";
};

# 3.建立地址库文件
cd /var/named
cp -p named.localhost example.com.zone    # BIND服务默认不给其他用户开放任何权限
vim example.com.zone
# --- 这一部分在不涉及DNS主从架构时，不起任何作用，但仍需要保持文件格式 ---
$TTL 1D
@       IN SOA  @ rname.invalid. (
                                        0       ; serial
                                        1D      ; refresh
                                        1H      ; retry
                                        1W      ; expire
                                        3H )    ; minimum
# --------------------------------------------------------------

# --- 这一部分是DNS服务器的声明信息，声明“哪个域名”由“哪个主机”负责，这两条记录是一个组合 ---
example.com.          NS    node1.example.com.    # “example.com”这个域名由“node1.example.com“主机负责
node1.example.com.    A     192.168.0.243         # ”node1.example.com“主机的IP是”192.168.0.243“
# ------------------------------------------------------------------------------
node2.example.com.    A     192.168.0.242

# 4.检查服务配置文件
named-checkconf    # 检查主配置文件语法是否正确
named-checkzone example.com.zone /var/named/example.com.zone    # 检查解析文件语法是否正确
dig -t A docker1.example.com @10.250.1.200 +short    # 测试dns服务解析

# 5.启动named服务
systemctl enable --now named
```

### 4.2 配置文件

BIND服务的主配置文件是`/etc/named.conf`，该配置文件的语法检测非常残酷，任意多出一个空格、少一个分号都可能导致服务异常，基于这个前提，对BIND服务的配置文件有2种建议的处理方式：

1. 严格基于默认的示例配置进行修改，勿随意修改任意符号或空格
2. 对于不需要的配置行，删除即可；BIND服务对没有在配置文件中显式声明的配置，允许范围较大。例如，默认BIND服务仅监听本地127.0.0.1，删除该配置行后，默认监听主机上所有IP。

#### 4.2.1 主配置文件解析

```bash
options {
	listen-on port 53 { 192.168.0.243; }; # 将监听地址改为内网地址192.168.0.243
	//listen-on port 53 { any; };	        # 监听IPv4地址，允许任何人链接
	listen-on-v6 port 53 { ::1; };	      # 监听IPv6地址的选项，用不到可删除
	directory       "/var/named";	        # 解析文件的路径目录，默认是相对路径
	dump-file       "/var/named/data/cache_dump.db";   # CACHE文件路径，指定服务器在收到rndc dump命令时，转储数据到文件的路径
	statistics-file "/var/named/data/named_stats.txt"; # 静态文件路径，指定服务器在收到rndc stats命令时，追加统计数据的文件路径
	memstatistics-file "/var/named/data/named_mem_stats.txt"; # 内存静态文件路径，服务器退出时，将内存统计写到文件的路径
	recursing-file  "/var/named/data/named.recursing"; # 指定服务器在通过rndc recursing名利零指定转储当前递归请求到的文件路径
	secroots-file   "/var/named/data/named.secroots";  # 在收到rndc secroots指令后，服务器转储安全根的目的文件的路径
	allow-query     { any; };    # 允许指定的客户端可以进行普通的DNS查询，默认为localhost，可以是关键词：any、localhost、none或IPv4、IPv6地址
	//allow-query-cache     { any; };    # 允许指定的客户端可以对缓存的访问
	forwarders		{ 10.250.1.254; };     # 指定上一级DNS服务器的IP，本机无法解析的域名会交给上一级进行解析
        
	recursion yes;    # 使用递归算法提供域名解析。权威DNS不需要开启递归，递归DNS需要开启递归服务，如果递归DNS具有公网IP需要设置访问控制来限制合法用户的查询

	dnssec-enable no; # 这里要把yes改为no，否则解析失败
	//dnssec-enable yes;    # 开启DNSSEC在权威或递归服务器之间的信任服务
	dnssec-validation no;   # 开启DNSSEC验证递归服务器

	bindkeys-file "/etc/named.root.key";

	managed-keys-directory "/var/named/dynamic";    # 指定目录，其中保存着跟踪被管理DNSSEC密钥文件，默认为工作目录

	pid-file "/run/named/named.pid";
	session-keyfile "/run/named/session.key";
};

logging {    # 开启DNS日志记录
	channel default_debug {
		file "data/named.run";
		severity dynamic;
	};
};

zone "." IN {    # 根域
	type hint;     # 域类型有hint（根域）、master（主DNS服务器）、slave（从DNS服务器）、forward等类型
	file "named.ca";    # 区域数据库文件名
};

include "/etc/named.rfc1912.zones";    # 正向解析规则和反向解析规则可以直接在主配置文件中写，也可以通过此文件集中保存
include "/etc/named.root.key";
```

主配置文件除了编写语法需要特别注意以外，还有些配置含义需要注意：

1. 地址库文件路径是在主配置文件中定义好的，使用include包函的配置文件并不修改地址库文件路径

   ```bash
   options {
   	directory       "/var/named";
   };
   include "/etc/named.rfc1912.zones";
   include "/etc/named.root.key";
   ```

2. 主配置文件中的zone区块声明的配置，每一行都需要注意其效果

   ```bash
   zone "example.com" IN {    # example.com意味着非根域，同时example.com也代表本zone区块的ORIGIN（原点），地址库文件中会频繁调用ORIGIN
           type master;       # 非根域不能使用type hint，非DNS主从架构的场景下使用master即可
           file "example.com.zone";    # 一个zone区块必须对应一个地址库文件，地址库文件必须存在，否则named服务无法正常启动
   };
   ```

3. include包函的配置文件实际上就是zone区块配置，zone区块的配置即可以直接写在主配置文件中，也可以写在include包函的配置文件中

   ```bash
   vim /etc/named.rfc1912.zones
   zone "example.com" IN {
       type master;
       file "example.com.zone";
       allow-update {none;};    # 允许特定客户端动态更新解析信息
   };
   ```

#### 4.2.2 地址库文件解析

```bash
vim /var/named/example.com.zone 
$TTL 1D    # 生存周期为1天
@       IN SOA         @      rname.invalid. (
                      0       ; serial    # 更新序列号；每次更新该文件序列号都应该增大
                      1D      ; refresh   # 更新时间；规定从域名服务器间隔多长时间查询一次主服务器，以保证从服务器的数据是最新的
                      1H      ; retry     # 重试延迟；从服务器尝试在主服务器上查询更新时，连接失败后，尝试重新连接的间隔时间
                      1W      ; expire    # 失效时间；从服务器向主服务器更新失败后间隔多长时间清除相应的记录
                      3H )    ; minimum   # 无效解析记录的缓存时间；用于设置缓冲服务器连接主服务器失败后间隔多长时间清除相应的记录
example.com.            NS      node1.example.com.
node1.example.com.      A       192.168.0.243
node2.example.com.      A       192.168.0.242
;                       AAAA    ::1
```

1. 所有FQDN末尾必须携带`.`，不带`.`的FQDN会被BIND服务自动追加`$ORIGIN`，以上述示例文件配置为例，`node1.example.com`（无点）实际会变成`node1.example.com.example.com`，这可能不会导致BIND服务运行报错，但明显域名解析会异常。

2. 地址库配置文件中所有的`@`都代表引用`$ORIGIN`

3. 地址库文件有一个”进化史“，基于BIND服务自动追加`$ORIGIN`的特性，地址库文件又可以简写部分配置

   ```bash
   example.com.    NS      node1    # NS声明的域名仍需要带.
   node1           A       192.168.0.243
   node2           A       192.168.0.242
   ```

4. 由于`NS`声明的域名写法错误率居高不下，于是又产生了新的简化配置

   ```bash
           NS      node1    # NS声明的域名直接为空，依靠BIND服务的自动补全$ORIGIN机制
   node1   A       192.168.0.243
   node2   A       192.168.0.242
   ```

6. DNS服务器只负责返回解析结果，但不能确保解析结果一定是正确的

   ```bash
           NS      node1    # NS声明的域名直接为空，依靠BIND服务的自动补全$ORIGIN机制
   node1   A       192.168.0.243
   node2   A       192.168.0.242
   node3   A       1.1.1.1  # 即便1.1.1.1这个机器并不存在，使用dig解析时仍能获取到此IP
   ```

### 4.3 主从架构

DNS主从架构本质是同一个DNS区域（Zone）由两台或多台权威服务器共同对外提供服务，主服务器持有可写的权威副本，从服务器持有只读副本，两者通过“区域传送（Zone Transfer）”保持数据一致。主从架构同时解决了单点故障、查询负载分摊、就近解析3件事。

- 消除单点故障：主从架构有多个DNS节点对外提供服务，单个节点的故障不影响域名解析
- 均衡查询负载：多个DNS节点都能应答，可以通过NS记录轮询或Anycast将流量摊开
- 就近解析：多个DNS从节点部署到不同地域，用户查询命中更近的节点，延迟更低

> **主从架构是平等的权威服务器**
>
> DNS从节点不是“备份机”，而是平等的权威服务器。客户端的域名解析查主还是查从，解析结果没有差别，主节点持有可写的地址库副本，从节点持有只读地址库副本，仅此而已。一个主节点可以对应多个从节点，从节点也可以再作为其它从节点的上游（级联同步）

#### 4.3.1 技术原理

主从同步靠三样东西协作：SOA 记录里的序列号、NOTIFY 通知、区域传送（AXFR/IXFR）：

1. 管理员在主节点上修改地址库文件，主配置文件也需要手动或自动递增SOA记录中的Serial（序列号）
2. 主节点向所有从节点发送NOTIFY消息（UDP 53端口），通知从节点区域产生变更
3. 从节点收到NOTIFY后，先向主节点查一次SOA记录，比对Serial：
   - 主节点Serial ≤ 本地Serial → 无需同步，结束
   - 主节点Serial > 本地Serial → 本地副本过期，触发区域传送
4. 从节点通过TCP 53端口发起区域传送请求
5. 主节点做授权校验（IP ACL和/或TSIG密钥），校验通过后流式下发记录
6. 从节点应用变更，随后用新数据应答查询

#### 4.3.2 配置

```bash
# 1.主节点调整主配置文件，允许指定从节点同步地址库文件
vim /etc/named.conf
allow-transfer { 192.168.0.242; };

vim /var/named/example.com.zone
example.com.    NS    node2
```



### 4.4 bind-chroot



bind-chroot修改了bind服务的主目录，bind-chroot所有的配置文件都在/var/named/chroot/目录下，包括所谓的"/etc/"和"/var/named/"目录，默认情况下，系统不加载bind-chroot服务，所以chroot目录下也没有任何配置文件，要使用chroot服务就需要先将正常的bind配置文件拷贝到chroot目录下

由于bind-chroot与bind存在细节上的差异，在未完全理解bind-chroot所有配置之前，建议主配置文件最好是精简最小化，需要什么配置就写什么配置，多余的配置可能会导致服务启动错误

```shell
# 1.拷贝bind配置文件到chroot目录
[root@infrastructure ~]# yum install -y bind bind-chroot
[root@infrastructure ~]# cp -p /etc/named.conf /var/named/chroot/etc/	#保持文件权限
[root@infrastructure ~]# cp -p /var/named/named.* /var/named/chroot/var/named/

# 2.编辑主配置文件（完整展示）
[root@infrastructure ~]# vim /var/named/chroot/etc/named.conf
options {
	listen-on port 53 { 172.16.0.254; };	#修改IPv4监听地址
	directory       "/var/named";
	allow-query     { any; };	#允许所有客户端进行DNS查询
	recursion no;	#仅作内网解析用途，此DNS服务器不联网，所以关闭递归
	pid-file "/run/named/named.pid";
	session-keyfile "/run/named/session.key";
};

zone "." IN {
	type hint;
	file "named.ca";
};

zone "example.com" IN {	#为"example.com"域做正向解析
	type master;
	file "example.com.zone";
};

zone "0.16.172.in-addr.arpa" IN {	#定义内网反向解析，网段需要倒写
	type master;
	file "172.16.0.arpa";
};
[root@infrastructure ~]# named-checkconf /var/named/chroot/etc/named.conf	#验证主配置文件是否有误

# 3.配置正向解析
[root@infrastructure ~]# cp -p /var/named/chroot/var/named/named.empty /var/named/chroot/var/named/example.com.zone
[root@infrastructure ~]# vim /var/named/chroot/var/named/example.com.zone
$TTL 1D
example.com.    IN SOA  infrastructure.example.com. rname.invalid. (
                                        0       ; serial
                                        1D      ; refresh
                                        1H      ; retry
                                        1W      ; expire
                                        3H )    ; minimum
                NS      infrastructure.example.com.
infrastructure  A       172.16.0.254
dns             CNAME   infrastructure

# 4.配置反向解析
[root@infrastructure ~]# cp -p /var/named/chroot/var/named/named.loopback /var/named/chroot/var/named/172.16.0.arpa
[root@infrastructure ~]# vim /var/named/chroot/var/named/172.16.0.arpa
$TTL 1D
0.16.172.in-addr.arpa.  IN SOA  infrastructure.example.com. rname.invalid. (
                                        0       ; serial
                                        1D      ; refresh
                                        1H      ; retry
                                        1W      ; expire
                                        3H )    ; minimum
        NS      infrastructure.example.com.
254     PTR     infrastructure.example.com.
```

一般不会用到bind的反向解析，反向解析基于网段实现




# NTP服务

NTP与Chrony都是用于同步计算机时钟的协议，它们都可以在计算机集群中实现时间同步，自CentOS 7开始Chrony已经作为默认的时间同步服务了，两者存在一些差异：

- 实现方式：NTP是一种传统的时间同步工具，基于UDP协议的C/S架构实现，使用一种复杂的算法来同步时钟；Chrony是相对较新的时间同步工具，使用"temporal median"算法估计时钟漂移率，平滑时钟跳变和抖动，来提高时钟同步的精度和稳定性

- 精度：Chrony相比NTP能提供更高的精度和更好的稳定性，尤其是在网络延迟较高的情况下，Chrony可以保持更好的同步精度，chrony支持本地时钟缓存，可以在没有网络连接时依然保持时钟的精度

- 配置：Chrony的配置相对简单，配置文件较少，相比NTP更易于管理，而且可以自动适应网络环境

- 安全性：NTP在安全性方面存在一些问题，因为它没有内置的身份验证机制。而Chrony支持加密和身份验证机制，可以提供更好的安全性
- 资源消耗：Chrony相比NTP对系统资源的消耗相对较少

## Chronyd

chronyd服务通过与配置的ntp服务器同步，保持本地硬件时钟（RTC）保持准确；或者无网络连接则与计算的RTC时钟飘移值同步，该值记录在/etc/chrony.conf文件中指定的driftfile中，默认情况下，chronyd使用NTP Pool Project的服务器同步时间，不需要额外配置。计算机处于孤立网络时，可能需要配置NTP，可以在/etc/chronyd.conf配置文件中配置两种类别的时间源

- server：比本地NTP服务器高一个级别
- peer：与本地NTP属于同一级别

可指定多个server和多个peer，每行指定一个，server行第一个参数是NTP服务器的IP地址或DNS名称，之后是该服务器参数选项，建议使用iburst选项，因为服务启动后会在短时间内执行四种测量，获得更精确的时间同步

### 主配置文件解析

```shell
server 0.centos.pool.ntp.org iburst	#指定ntp服务器地址，服务端不能上网的情况下可以指定本机IP，设置本机为时间服务器
server 1.centos.pool.ntp.org perfer	#perfer表示优先
server 210.72.145.44 iburst	#中国国家授时中心的IP
server 3.centos.pool.ntp.org iburst

driftfile /var/lib/chrony/drift	#chronyd程序的主要行为之一，就是根据实际时间计算出计算机增减时间的比率，将它记录到一个文件中是最合理的，它会在重启后为系统时钟作出补偿，甚至可能的话，会从时钟服务器获得较好的估值

makestep 1.0 3	#通常，chronyd将根据需求通过减慢或加速时钟，使得系统逐步纠正所有时间偏差，在某些特定情况下，系统时钟可能会漂移过快，导致该调整过程消耗很长的时间来纠正系统时钟。该指令强制chronyd在调整期大于某个阀值时步进调整系统时钟，但只有在因为chronyd启动时间，超过指定限制（可使用负值来禁用限制），没有更多时钟更新时才生效，此处表示如果调整值大于1秒，则这将使系统时钟步进，但仅在前十个时钟更新中

rtcsync	#rtcsync指令将启用一个内核模式，在该模式中，系统时间每11分钟会拷贝到实时时钟（RTC）

#hwtimestamp *	#在所有支持硬件的接口上启用硬件时间戳,系统默认

#minsources 2	#增加需要调整的最小可选信号源数量 系统时钟。系统默认

#allow 192.168.0.0/16	#可以指定一台主机、子网，或者网络以允许或拒绝NTP连接

#local stratum 10	#如果上面使用server字段配置的时间服务器同步时间失败，默认情况下当前时间服务器是不会向客户端同步时间的。这是因为担心当前节点的时间不准确(因为当前节点没有和定义中的server时间服务器进行同步)。如果我们想要在server指定的时间服务器同步失败的情况下依旧返回当前时间服务器的时间给客户端，需要开启该参数,生产环境开启该参数会有一个问题，如果server有配置，那么可能会导致所有服务器的时间都是一致的，并且都是错误的。如果是非互联网环境，例如私有云等或独立局域网，即使都出错也可以接受

#keyfile /etc/chrony.keys	#指定密码文件

logdir /var/log/chrony	#指定日志文件的目录
```

**服务端配置**

```shell
[root@infrastructure ~]# yum install -y chrony
[root@infrastructure ~]# vim /etc/chrony.conf	#仅展示修改处
#server 0.centos.pool.ntp.org iburst
#server 1.centos.pool.ntp.org iburst
#server 2.centos.pool.ntp.org iburst
#server 3.centos.pool.ntp.org iburst
Server 127.0.0.1 iburst
allow 0.0.0.0/0
local stratum 10
[root@infrastructure ~]# systemctl restart chronyd
```
