# Linux 软件包管理

## 一、RPM 包管理

### 1.1 RPM 概述

RPM（RedHat Package Manager）由RedHat公司提出，RedHat、SUSE等发行包通用。Linux系统上的软件包状态信息会自动的集中记录到软件包的数据库中，这个数据库由Linux系统自动维护，用于记录软件包安装、卸载、版本等变化信息，分析软件包依赖关系（在windows系统中是依赖注册表来实现这个功能的）。RPM软件包的包名一般都比较长，这是为了使管理员能够得到更多的信息，以`firefox-52.7.0-1.el7.centos.x86_64.rpm`包名为例，其每个字段分别代表着`软件名-版本信息.操作系统.硬件架构.rpm`

相比较Windows的软件安装，RPM包的安装过程没有所谓“下一步”的提示、不允许用户自定义安装路径、不允许用户自定义安装的功能，RPM包的安装路径、安装功能在软件包内直接写为固定参数，回车即代表着软件包的安装。虽然RPM包不允许选择安装路径与功能，但它同样也存在一些常见的安装路径：

| 文件类别             | 默认安装位置                     |
| -------------------- | -------------------------------- |
| 普通执行程序         | /usr/bin/、/bin/                 |
| 服务器程序、管理工具 | /usr/sbin/、/sbin/               |
| 配置文件             | /etc/、/etc/软件名/              |
| 日志文件             | /var/log/、/var/log/软件名/      |
| 程序文档、man手册页  | /usr/share/doc/、/usr/share/man/ |

### 1.2 RPM 安装与查询

```bash
# 安装
rpm -ivh package.rpm
	-i：执行安装；安装的软件包存在其他依赖关系时，RPM安装软件会失败
	-v：显示详情
	-h：显示进度条
	-U：升级软件包
	--nodeps：忽略依赖安装（不推荐）
	--force：强制覆盖安装
	--test：测试安装，不做真实安装动作

# 查询；-q选项的组合查询的都是已安装的软件包信息，结合-p选项后可以查询未安装的软件包信息
rpm -qa | grep openssh-server    # 查找openssh-server包
rpm -qa                          # 列出所有已安装的包
	-ql：列出包的所有文件
	-qi：查看包信息
	-qc：查看包配置文件
	-qd：查看包文档文件
	-qf：显示文件或命令属于哪个软件包
	-p：显示指定的软件包信息
rpm -qi openssh-server    # 查询软件的详细信息
rpm -ql openssh-server    # 查询软件各文件的安装路径
rpm -qf /etc/hostname     # 根据文件名逆向查询该文件属于哪个软件包，需要输入文件路径
rpm -qpi /mnt/cdrom/AppStream/Packages/v/vsftpd-3.0.5-10.el10.x86_64.rpm    # 使用p选项时必须指定完整的软件包名称
rpm -qpl /mnt/cdrom/AppStream/Packages/v/vsftpd-3.0.5-10.el10.x86_64.rpm    # 可以查到该软件的预安装路径（-qp=query package）
rpm -q --scripts openssh-server    # 查看包安装/卸载脚本
```

使用`rpm -q nginx`同样可以查询当前linux系统中是否有安装名为“nginx”的包，这种方式与grep过滤的区别在于，`rpm -q`是严格匹配，任意一个字符的变化都会导致`rpm -q`查询不到软件包。除此以外，linux系统本身还有一个特性：在linux系统中安装的包名，与软件包安装后使用的命令，可能是不相同的。比如说，`rpm -q vim`查不到名为vim的包，但vim命令仍可以正常使用。

`rpm -qpl`命令的解析说明可能略有歧义，使用`-p`参数时必须指定某个软件包名，其作用是查看如果要安装这个软件包，会在linux系统上产生哪些文件。如果说`rpm -ql`是先安装软件包、再查询该软件包安装过程中产生了哪些文件；那么`rpm -qpl`就是在安装软件包之前、就先查看安装该软件包会产生哪些文件。

基于RPM软件包的数据库机制，`rpm -qf`查询的文件即便在Linux系统上删除了该文件，大多数情况下也是能够查询到该文件所属的软件包信息的，当文件在Linux系统上被删除后，RPM仍能够查询数据库中的记录，但这种方式并不是绝对通用的

### 1.3 RPM 升级与卸载

```bash
# 升级
rpm -Uvh package.rpm              # 升级（没装过则安装）
rpm -Fvh package.rpm              # 强制升级（没装过则不安装）

# 卸载
rpm -e nginx                      # 卸载（包名，不是文件名）
rpm -e --nodeps nginx             # 忽略依赖卸载
rpm -e --allmatches nginx         # 卸载所有匹配版本
```

### 1.4 RPM 签名验证

在CentOS 7版本下，使用本地挂载镜像的方式安装、查询软件包的详细信息时会产生一个警告，这个警告本身对软件包没有任何的影响，大多数情况下可以不必理会此告警。2种场景下会产生该告警：软件包内确实没有签名信息、操作系统不识别软件包的签名信息。产生此告警的原因是出于系统软件的安全性考虑，早期由于Linux平台的开源，黑客会将恶意代码写入软件的源代码中，导致系统安装该软件时就会被劫持。为了避免这种情况，Linus联合RedHat将市面上常用的开源软件全部进行了一遍检测，确保软件正常后RedHat会在软件包内做一个签名信息。

软件包的详细信息中产生的NOKEY告警，代表着Linux系统在该软件包中没有发现RedHat的签名信息。但实际上是有RedHat签名的，因为软件包来自ISO镜像，而ISO镜像又是由RedHat全球发布的，此处产生NOKEY告警的原因是因为系统不识别RedHat的签名信息，导致系统认为软件包没有签名。RedHat的签名信息存放在ISO镜像的`/mnt/cdrom/RPM-GPG-KEY-CentOS-7`路径下，只需要手动导入RedHat的签名信息即可解决此告警，由于该告警并不会影响到软件包的正常使用，一般情况下也不会单独去导入RedHat的签名信息。

Rocky 10版本似乎没有出现这个问题，即便不手动导入证书，也没有产生告警信息。

## 二、YUM/DNF 包管理

### 2.1 YUM 概述

RPM包的一个特性是，当A程序的运行需要python环境时，A软件包可能会将python环境打包到RPM包中，如果B程序也需要python环境，B软件包可能会直接做一个判断，“系统中是否已安装A包”，如果没有就需要先安装A包，这就是依赖关系。linux系统发展至今，各个软件包之间的依赖关系已经是无法避免的一个问题，要安装一个软件包，可能会牵扯到非常多的依赖包，通过人工解决这个问题已经变得异常困难，于是YUM产生了。

YUM（Yellowdog Updater Modified）是基于RPM的包管理器，它构建的软件更新机制实现了自动解决软件包之间的依赖关系，使用`yum`安装一个软件包时，`yum`会自动分析并下载安装其所需的所有其他软件包（依赖），免去了手动寻找和安装的繁琐过程，但所有的软件包均由集中的YUM软件仓库提供。因此，与RPM包管理不同的是，YUM是无法直接使用的，在使用YUM之前必须先搭建YUM软件仓库。YUM使用最常见的C/S结构，YUM软件包仓库实际上就是指的Server端，Server端由两部分组成：软件包、仓库数据文件；仓库数据文件用于记录众多软件包的状态信息，类似于菜单的作用。

YUM的搭建一般分为两种模式：本地YUM仓库和远端YUM仓库，本地YUM仓库将Server端和Client端集中存放在本机机器上，无需网络连接；远端YUM仓库则需要通过FTP协议或HTTP协议将软件包从Server端下载到本地进行安装，在使用YUM安装软件包时，默认情况下会跟用户再次确认是否安装软件，此时用户可以选择确认安装、拒绝安装或仅下载软件包到本地但不安装。

### 2.2 YUM仓库搭建

常规情况下，各个linux发行版的iso镜像文件中已经打包好了软件包和仓库数据文件，因此YUM Server端的配置在挂载iso镜像的那一刻就已经完成了，以Rocky Linux为例，其软件包和仓库数据文件分别存放在`AppStream/Packages`、`AppStream/repodata`两个目录下，所以本地YUM仓库的搭建主要是YUM Client相关的配置。

YUM Client的配置同样有几个注意事项，所有的Client配置文件都必须集中存放在`/etc/yum.repos.d/`目录下；允许存在多个Client配置文件，但所有配置文件需要以`.repo`为后缀；任意一个`.repo`的Client配置文件有误，都会影响到所有的Client配置，导致YUM不可用。

```bash
mkdir /mnt/cdrom                   # 创建挂载点
mount /dev/sr0 /mnt/cdrom          # 挂载镜像
vim /etc/yum.repos.d/local.repo    # 新建本地YUM Client配置文件
[local]                                   # yum源名称，具有唯一性
name = Local Repository                   # yum仓库的描述信息
baseurl = file:///mnt/cdrom/AppStream/    # 指定yum server的位置；本地YUM仓库与远端YUM仓库的区别仅在于此参数是否为本地路径
enabled = 1                               # 是否启用此yum源配置
gpgcheck = 0                              # 关闭签名验证
#gpgkey = /mnt/cdrom/RPM-GPG-KEY-Rocky-10 # 启用签名验证时，需要指定签名文件位置；不启用验证的情况下无需配置此选项

yum repolist                       # 列出系统当前可用的yum仓库，一般也用于配置完YUM Client配置文件后进行验证
```

### 2.3 基础命令

```bash
# 查询
yum list                          # 列出YUM仓库中的所有软件
yum list installed                # 列出已安装的包
yum list httpd                    # 查找YUM仓库中名为httpd的软件，使用list查询软件是严格匹配软件名称
yum search httpd                  # 查找YUM仓库中名为ftp的软件，使用search查询软件是模糊匹配软件，此处“模糊匹配”并非只匹配软件名，只要软件能够实现相应功能的也会被匹配。以httpd为例，search httpd会匹配到curl工具，因为curl工具会使用到httpd功能
yum provides /usr/sbin/nginx      # 通过命令或文件逆向查询命令所属的软件包，与rpm -qf不同的是，YUM基于软件仓库的查询，不仅是只针对已安装的软件包进行查询
yum info nginx                    # 查看包信息

# 安装/升级/卸载
yum install -y nginx              # 默认情况下YUM检测软件包的依赖关系后会交互式确认是否需要安装，-y参数表示取消交换式确认
yum reinstall -y nginx            # 覆盖性的重新安装，某些场景下误操作删除了某个软件包中的可执行程序时，再次安装该软件包会提示已安装，此时就需要覆盖安装，使软件包重新生成可执行程
yum localinstall package.rpm      # 本地安装（自动处理依赖）
yum update nginx                  # 升级
yum update                        # 升级所有包
yum remove nginx                  # 卸载（自动卸载依赖）
yum erase nginx                   # 卸载（更彻底）

# 缓存管理
yum makecache                     # 生成缓存
yum clean all                     # 首次yum repolist时才会去读取YUM配置文件，之后YUM会将数据缓存在内存中。当YUM配置文件被修改后，就需要清空YUM缓存，使YUM重新读取配置文件
yum clean metadata                # 清除元数据缓存
```

执行`yum remove`时不建议带上`-y`选项，`yum remove`在卸载软件时会自动判断卸载目标软件包后，有哪些其他包无法独立运行，无法独立运行的包都会作为目标软件包的依赖包一同卸载。例如，`yum remove httpd`在卸载httpd包时，yum判断mod_http2包在卸载httpd包之后无法独立运行，那么mod_http2这个包也会被一并卸载，如果此时又有其他软件包依赖mod_http2运行，那么相应的包也会一并被卸载。

所以`yum remove`的影响范围不可控，在执行卸载命令时不带上`-y`选项是留有一定的余地，避免重要的软件被一并卸载。

> **缓存管理**
>
> yum本身的缓存管理功能是为了提高运行效率，首次执行`yum repolist`时，yum会自动将yum仓库的元数据保存到本地磁盘，并在内存中生成缓存数据，下次再执行`yum repolist`时就会从内存中直接读取缓存数据。也由于这个机制，一旦管理员手动修改了yum配置文件，`yum repolist`仍会从内存中读取数据，这导致最新的yum配置文件无法生效，这种场景下就需要清理缓存。
>
> 还有一个冲突的点，既然有了`yum repolist`命令，为什么还需要`yum makecache`命令生成缓存呢？`yum repolist`的本职工作是查看yum仓库的状态，下载元数据、生成缓存都只是顺带做的事；`yum makecache`的主要功能就是下载元数据，`yum makecache`或`yum makecache --force`可以越过缓存机制强制从yum仓库下载最新的元数据。在RHEL 10版本，`yum makecache` 被设计为一个独立的系统定时器（`dnf-makecache.timer`）。系统会每天定时在后台自动执行 `dnf makecache`，确保缓存始终是最新的，`yum repolist`几乎已经不在承担下载功能。

### 2.6 自建YUM仓库

建立YUM源服务端，常见的方式有2种：一种是将本地iso镜像挂载到系统，直接下发iso镜像中的软件包，由于ISO镜像中仓库数据文件是自带的，存放在`/repodata/`路径下，因此本地iso镜像的方式建立YUM源服务比较简单；另一种是将外网YUM源的包同步到本地后再下发。`reposync`工具就用于将外网yum源的包同步到本地，`reposync`工具被包含在`yum-utils`包中，所以要使用`reposync`命令时需要安装`yum-utils`包；通过`reposync`同步外网软件包后，还需要通过`createrepo`命令生成本地的仓库数据文件，为存放于本地的众多RPM软件包提供索引，自动化分析各软件包之间所需依赖关系，并生成元数据。

通过`yum repolist`命令可以查看系统中配置了哪些网络yum，并查看其对应的`repo id`，`reposync`命令也可以通过`--repoid=[repo id]`选项，只同步指定的源到指定目录

#### 2.6.1 操作步骤

1. 在主机上添加一个远端yum配置文件（以docker的官方配置为例）

   ```bash
   dnf -y install dnf-plugins-core
   dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
   ```

2. 安装YUM Server的配置工具

   ```bash
   dnf install -y createrepo_c yum-utils httpd
   systemctl enable --now httpd
   ```

   CentOS 7版本需要执行`yum install -y createrepo yum-utils httpd reposync`，但在Rocky 10版本，reposync工具已经被整合为dnf命令的内置功能，无需单独安装，createrepo包也被重命名为createrepo_c。

3. 创建YUM Server的Web目录

   ```bash
   mkdir /var/www/html/yumrepos/
   ```

4. 同步互联网YUM仓库的软件包到YUM Server本地

   ```bash
   reposync -p /var/www/html/yumrepos/    # 缺省情况下同步所有远程YUM仓库的软件包到本地，量会特别大
   	-p：指定下载路径
   	-n：仅下载最新版本的包，跳过旧版
   	-q：静默模式，减少输出
   	-r (--repoid)：指定仓库ID，可多次使用
   	--delete：删除远程仓库中已经不存在的本地软件包
   	-c：指定配置文件运行（默认配置文件是 /etc/yum.conf ）
   	
   # 语法示例
   # yum repolist    # 查看各个YUM仓库的repoid
   # reposync -n --repoid base --repoid updates -p /var/www/html/yumrepos/
   # reposync -n --repoid ceph --repoid ceph-noarch -p /var/www/html/yumrepos/
   # reposync -n --repoid centos-openstack-train -p /var/www/html/yumrepos/
   # reposync -n --repoid centos-qemu-ev -p /var/www/html/yumrepos/
   # reposync -n --repoid zabbix -p /var/www/html/yumrepos/
   reposync -n --repoid docker-ce-stable -p /var/www/html/yumrepos/
   ```

5. 创建仓库数据文件

   ```bash
   for i in /var/www/html/yumrepos/*; do cd $i && createrepo .; done
   ```

6. 定期更新YUM Server的yum仓库

   ```bash
   reposync -n --repoid=docker-ce-stable -p /var/www/html/yumrepos/
   cd /var/www/html/yumrepos/base/
   createrepo --update
   ```

7. YUM Client的yum配置文件示例

   ```bash
   vim /var/www/html/private.repo
   [docker]
   name=YUM Server Docker-CE-Stable
   baseurl=http://[YUM Server]/yumrepos/docker-ce-stable/
   gpgcheck=0
   enabled=1
   ```

## 三、系统服务管理

### 3.1 systemctl 基础命令

```bash
# 启动/停止/重启
systemctl start nginx
systemctl stop nginx
systemctl restart nginx           # 重启
systemctl reload nginx           # 重载配置（不中断服务）

# 查看状态
systemctl status nginx
systemctl is-active nginx        # 查看是否运行
systemctl is-enabled nginx       # 查看是否开机启动

# 开机启动
systemctl enable nginx           # 开机启动
systemctl disable nginx          # 禁用开机启动
systemctl enable --now nginx    # 启动+开机启动
systemctl disable --now nginx   # 停止+禁用开机启动

# 查看
systemctl list-units --type=service --all   # 列出所有服务
systemctl list-dependencies nginx           # 查看服务依赖
systemctl cat nginx                          # 查看服务配置文件
```

### 3.2 运行级别（target）

| SystemV runlevel | systemd target | 说明 |
| :--- | :--- | :--- |
| 0 | runlevel0.target, poweroff.target | 关机 |
| 1 | runlevel1.target, rescue.target | 单用户救援模式 |
| 2 | runlevel2.target, multi-user.target | 多用户（无NFS） |
| 3 | runlevel3.target, multi-user.target | 多用户（命令行） |
| 4 | runlevel4.target, multi-user.target | 多用户（保留） |
| 5 | runlevel5.target, graphical.target | 图形界面 |
| 6 | runlevel6.target, reboot.target | 重启 |

```bash
# 切换运行级别
systemctl isolate multi-user.target    # 切换到命令行
systemctl isolate graphical.target      # 切换到图形界面

# 设置默认级别
systemctl set-default multi-user.target   # 命令行
systemctl set-default graphical.target     # 图形界面

# 查看默认级别
systemctl get-default
```

### 3.3 服务配置文件

systemd 服务配置文件位于：

| 目录 | 说明 |
| :--- | :--- |
| `/usr/lib/systemd/system/` | 软件包提供的服务文件 |
| `/run/systemd/system/` | 运行时创建的服务（不持久） |
| `/etc/systemd/system/` | 系统管理员创建的服务（优先） |

```bash
# 示例：创建自定义服务
vim /etc/systemd/system/myservice.service
[Unit]
Description=My Service
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/myservice
Restart=on-failure
User=root

[Install]
WantedBy=multi-user.target

# 重载systemd配置
systemctl daemon-reload
systemctl enable --now myservice
```
